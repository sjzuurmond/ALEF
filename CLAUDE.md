# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

ALEF (Agile Law Execution Factory) is a JetBrains MPS-based language workbench built by the Dutch Tax
Administration (Belastingdienst). It lets non-programmers write executable Dutch tax-law business rules
in a controlled-natural-language DSL called **Regelspraak**, and compiles them into runnable services.
Almost the entire codebase *is* MPS: languages, editors, type systems and generators defined as MPS models
(`.mps`/`.mpl`/`.msd`/`.devkit` XML-ish files), plus a handful of plain Maven/Java modules under `AlefJava/`.

User-facing documentation (in Dutch) lives in `docs/` and is built into the "ALEF handleiding" with
Zensical/mkdocs (see `mkdocs.yml`). It's the best source for domain vocabulary — see the glossary below.

## Build

The whole build is Maven-orchestrated but does almost all real work by shelling out to MPS's Ant-based
build system. There is no lightweight build — building anything downloads a full MPS distribution + JBR
+ itemis MPS extensions (several hundred MB–GB) from `https://artifacts.itemis.cloud/repository/maven-mps`,
then runs MPS headless to generate, compile and test every language/plugin/solution.

```bash
# Install/refresh only the MPS + JBR + extension dependencies (fast path, no generate/build/test)
mvn -B -U -Pinstall-deps package

# Full build: downloads deps, generates all languages, compiles, runs the platform test suite,
# and produces distributions in build/artifacts/alef-distribution (win/linux/mac zips/tarballs)
mvn -U package
```

CI (`.github/workflows/build.yml`) runs on JDK 21 + Python (for docs) via
`xvfb-run -- mvn -B package` — MPS's headless Ant tasks still need a virtual display on Linux.

Required local setup for interactive development (from `README.md`):
1. OpenJDK 17+ and Maven installed.
2. JetBrains MPS installed at the version pinned in `versionMPS.txt` (currently MPS 2025.1 —
   see `alef-plugin-pom.xml` for the exact `mps.version`/`extensions.version`/`jbr.version`).
3. Run `mvn -B -U -Pinstall-deps package` once to fetch dependencies.
4. Open the repo root (where `README.md` lives) as a project in MPS.
5. In MPS Settings → Appearance & Behavior → Path Variables, add `alef.home` pointing at the repo root
   (models reference this macro).
6. Use MPS's **Build → Rebuild Project** to generate/compile everything from inside the IDE.

### What actually drives the Maven build

`pom.xml` → `alef-plugin-pom.xml` does the real work via `exec-maven-plugin`:
- `deps`/`copy-jbrs`/`copy-batik`/`copy-*-dependencies` executions (init/compile phases) unpack the
  downloaded MPS distro, JBR, and itemis extensions into `target/`, and stage third-party jars
  (Apache Batik, POI) into the `solutions/org.apache.*/lib` folders MPS modules reference.
- `build-alef` execution (`compile` phase) runs `scripts/build-plain.sh`.
- `build-services` execution (`test` phase) runs the built `alefProjectBuild.jar service` command.

`scripts/build-plain.sh` calls `scripts/doAnt.sh` (a thin wrapper that runs MPS's bundled Ant with the
MPS classpath and lots of `-D` build metadata) against a long, ordered sequence of Ant build files —
`plugins/build-extensions/build_build_extensions.xml`, `build_build.xml`, each plugin's own
`*-mpsplugin.xml`/`*-tests.xml`, `alef-standalone.xml`, `alef-distribution.xml`, and finally
`alef-test.xml` (`clean generate build test`). Order matters: plugins that other modules depend on
(build-extensions, json, projecthygiene, translator, linguistics) are built before the main `build_alef`
chunk.

**Important:** `build_build.xml` is the *only* Ant build file committed to git. Every other `*.xml` build
script referenced above (`alef-test.xml`, `alef-distribution.xml`, `*-mpsplugin.xml`, `*-tests.xml`, etc.)
is generated by MPS from a corresponding **build-solution model** and is gitignored (see `.gitignore`).
Never hand-edit a generated `.xml` build file — edit the source build-solution model instead
(e.g. `solutions/build_alef/`, `solutions/build_aleftest/`, `plugins/<name>/solutions/<name>.build/`)
inside MPS and regenerate. Likewise, `source_gen/`, `classes_gen/`, `test_gen/` under any module are
generated output and gitignored.

## Testing

There are two unrelated notions of "test" in this repo — don't confuse them:

1. **Plain JUnit tests** in the `AlefJava/*` Maven modules (e.g. `AlefJava/alefRuntime/src/test/java/...`,
   using JUnit 5). These run the normal way: `mvn test` from `AlefJava/<module>`, or filtered with
   `mvn -Dtest=ClassName#methodName test`.
2. **Platform test solutions** — MPS solutions named `*_Test` (e.g. `RegelCondities_Test`,
   `TypeSystem_Test`, `Servicespraak_Test`, `Editor_Test`, `Hygiene_Test`) that verify the languages,
   editors, type system and generators themselves. These use MPS's built-in test languages
   (`jetbrains.mps.baseLanguage.unitTest`, `jetbrains.mps.lang.test`) declared in each module's `.msd`.
   They are all bundled into one Ant test target, generated from `solutions/build_aleftest/models/build_aleftest.mps`
   into the (gitignored) `alef-test.xml`, and run together via
   `scripts/doAnt.sh -f alef-test.xml clean generate build test` (part of `build-plain.sh`, i.e. `mvn package`
   runs the entire suite — there is no `-Dtest=`-style single-module filter for this Ant target). To run
   just one platform test module during development, either use MPS's IDE "Run Tests" action on that
   specific `*_Test` solution/model, or temporarily trim the `alefTests` group in
   `solutions/build_aleftest/models/build_aleftest.mps` and regenerate.
3. Separately, **Testsets** are a Regelspraak-domain concept (`docs/testen/Testen.md`,
   `docs/testen/Testset.md`) for testing the *business rules an ALEF project author writes* — attributes,
   rules, rule groups, flows, services — from inside ALEF Studio. This is end-user functionality, not a
   CI concept, and is unrelated to the two test mechanisms above.

## Repository layout & architecture

```
languages/    MPS languages (the DSLs and their generators)
solutions/    MPS solutions: runtime libraries, platform test suites, build-solution models, tooling
plugins/      Standalone MPS IDE plugins, each with its own build pipeline (build-extensions, json,
              linguistics, projecthygiene, translator)
devkits/      MPS devkits bundling which languages/solutions/generation-plan are available to end users
AlefJava/     Plain Maven/Java modules (non-MPS): alefRuntime, merlin, servicelogger,
              serviceTestRuntime, alefProjectBuild, testReport, LoggerExample
docs/         Dutch end-user documentation (mkdocs/Zensical)
```

Directory names don't always match module names — e.g. the `gegevensspraak` language module lives inside
`languages/objecten/gegevensspraak.mpl`, and `testspraak` lives inside `languages/validatie/testspraak.mpl`.
When looking for a language/solution, search by module name (grep `.mpl`/`.msd` files or module ids),
not by directory name.

### The Regelspraak language family and the "merlin" generator split

The user-facing "spraak" languages (`regelspraak`, `besturingspraak`, `gegevensspraak`, `servicespraak`,
`bronspraak`, `vrijspraak`, `beslistabelspraak`, `testspraak`) are the editable controlled-natural-language
DSLs: each defines `structure` (AST/grammar), `editor` (projectional editor cells rendering the CNL
surface syntax), `typesystem`, `constraints`, `behavior`, `actions`, `dataFlow` and `intentions` aspects,
but generally **no generator of their own**.

Each has a corresponding **`merlin<X>`** language (`merlinRegels`, `merlinBesturing`, `merlinGegevens`,
`merlinService`, `merlinTabellen`, `merlinBuild`, `merlinTests`, plus `.tijd` variants) that
`extendedLanguage`s + `generate-into`s the spraak language and carries the actual code generator
(`languages/merlin<X>/generator/templates/...`) that lowers rule/data models into runtime constructs
backed by `AlefJava/alefRuntime` and `AlefJava/merlin`. "Merlin" is a purely internal implementation
codename — it never appears in end-user documentation. The overall generation pipeline is wired up as
MPS generation-plan models under `solutions/spraken.genplan/` (e.g. `merlin@genplan`, `alef@genplan`).

`.tijd` variants (`gegevensspraak.tijd`, `regelspraak.tijd`, `merlinGegevens.tijd`, ...) extend their base
language to add the temporal/versioning dimension that lets law change over time — every Regelspraak rule
has one or more "Regelversies", each valid during a "Geldigheidsperiode" (validity period).

Two devkits bundle these for end users (`devkits/*/*.devkit`):
- `alef.devkit` — the full platform: all spraak + merlin languages, `bronspraak`, `vrijspraak`,
  `rapporten`, generation plan `alef@genplan`.
- `standaard.devkit` — a minimal data-model-only subset (`gegevensspraak` + `merlinGegevens`,
  generation plan `standaardMerlin@genplan`) for projects that don't need rules/services/orchestration.

### Plugins

- `build-extensions` — MPS-language tooling that models/generates this repo's own Ant build scripts and
  project-consistency checks.
- `json` — a meta-language describing JSON-shaped data structures (schema/tooling), distinct from the
  runtime JSON parsing exercised by `solutions/JSONParse_Test`.
- `linguistics` — attaches Dutch grammatical metadata (word forms/conjugation) to language concepts so
  generated/edited Regelspraak sentences stay grammatically correct.
- `projecthygiene` — naming/deprecation/completeness checks enforced on language and model structure
  during build.
- `translator` — attaches translation/localization metadata to language concepts.

### Domain glossary (from `docs/`)

- **Regelspraak** — controlled natural language for versioned business rules ("Regelversies", each valid
  during a "Geldigheidsperiode").
- **Besturingspraak** — defines "Regelgroepbundels": collections of rule groups applicable to a test or
  service (the older "Flow" concept is deprecated).
- **Servicespraak** — defines deployable SOAP/REST services that let external systems execute the rules.
- **Bronspraak** — small language for citing legal sources/law articles inline within rules.
- **Vrijspraak** — grammatically structured free-text/explanatory prose embedded in rules.
- **Objecttype** — a data type with attributes and "kenmerken" (derived boolean characteristics); can be
  "bezield" (animate/legal person) or "onbezield" (inanimate), which affects rule syntax.
- **Feittype** — a relation between two object types via named roles.
- **Domein** — a project-specific data type: an enum-like value list, or a named wrapper around a
  general data type.
- **Beslistabel** — a decision-table presentation of a set of equivalence rules (condition/conclusion
  columns, one row per equivalent rule).

## Working conventions

- Branch naming: `feature/<ticket-number>`, `hotfix/<ticket-number>`, `bugfix/<ticket-number>`
  (see `CONTRIBUTING.md`); `develop` is the main integration branch, `(n-1).x`/`(n-2).x` are
  maintenance branches accepting hotfixes only.
- Commit messages should include the ticket number and a short description.
- Pull requests are merged **fast-forward only** — the team relies on MPS's model merge driver
  (`.gitattributes` registers `merge=mps` for `.mps`/`.mpl`/`.msd`/`.devkit`/`.mpr`/`.mpsr`/`.model`
  and `trace.info`/`generated`/`dependencies` files) rather than 3-way merges of these XML-ish files.
- Contributions are under the EUPL 1.2 license (see `LICENSE.txt`); PRs must state this.
